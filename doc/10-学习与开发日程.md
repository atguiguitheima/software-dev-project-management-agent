## 0. 三条线的基本原则

| 线 | 节奏 | 铁律 |
|----|------|------|
| **学习线** | 跟着开发走，不独立成段 | **学一点、立刻用**——每个知识点必须配一个当天能跑通的验证产出，禁止"先学完一个月再动手" |
| **开发线** | M1→M10，每步独立可验证 | **M2 是地基**，M2 没跑通之前不碰任何业务功能 |
| **论文线** | 边做边写，不做完再写 | 第 1~3 章靠设计文档直接生成，第 4 章跟着代码写，第 5 章靠 `agent_runs` 的真实数据 |

**为什么学习线不独立成段**：这是本日程最重要的一条设计。把"学 Go 并发""学 Milvus"排成独立的学习阶段，学完三天后就忘，而且学的时候不知道哪些是真问题。正确做法是——**先遇到真问题（比如"Webhook 重发了，我的库里出现两条"），再带着问题去学幂等与唯一索引**。你的记忆和理解深度完全不一样。

### 时间预算（务必现实）

| 时期 | 每周投入 | 说明 |
|------|---------|------|
| 学期中（11 月—1 月中、3 月—5 月） | **15~20 h** | 工作日 2h/晚 × 5 + 周末 5~8h |
| 期末考周（约 2 周） | **5 h** | 只做维护性任务，不接新模块 |
| **寒假（1 月中—2 月底，6 周）** | **30~35 h** | **全项目 60% 的代码在这 6 周产出** |
| 春节周 | 15 h | 人情刚需，别硬扛 |
| 答辩前 2 周 | 20 h | 论文为主，代码只修 bug |

**一个反直觉但重要的提醒**：寒假前别把硬骨头全留着。因为 M6~M9（对话、提醒、RAG、需求拆解）是论文第 4 章的骨架，如果寒假结束时它们还不稳，3 月你就要一边改代码一边写论文，那是最痛苦的状态。**目标状态：开学（2/26）时代码已功能完整，3 月只做试用、采集数据、写论文。**

## 1. P0 奠基期（11/03 — 11/29，4 周）— 打通 LLM 与 Agent 循环

**任务书节点**：教师拟题（11/15-17）、导师确认（11/23-24）、动员会（11/25）、拟定任务书（11/26-30）。这些是行政节点，不占用你的开发时间。

| 周 | 学习目标 | 开发任务 | 验收 |
|----|---------|---------|------|
| W1<br>11/03-09 | Go 并发基础自查（goroutine/channel/context 取消）；OpenAI 兼容协议（messages、tools、usage 字段） | **M1**：LLM 客户端封装（重试、超时、token 计数）+ 命令行聊天程序 | 终端能连续对话；断网重试生效；每次调用打印 token 消耗 |
| W2<br>11/10-16 | 精读 ReAct 论文 + Anthropic《Building Effective Agents》；搞懂 Function Calling 的请求/响应结构 | **M2-A**：工具注册表（name + JSON Schema + 执行函数） | 一个假工具 `get_current_time` 注册成功，Schema 能通过校验 |
| W3<br>11/17-23 | 循环护栏设计：最大步数、工具超时、结果截断；理解"模型为什么不调工具"的典型原因 | **M2-B**：ReAct 主循环（解析 tool_calls → 执行 → 回填 → 再调模型） | 问"现在几点"模型能正确调工具并组织回答；问"你好"**不**调工具 |
| W4<br>11/24-30 | MySQL 8 安装 + JSON 类型 + utf8mb4 三处配置；GORM 基础（模型定义、事务闭包） | **M2-C**：给 Agent 加两个真工具（`list_open_prs` 先返回假数据）+ `agent_runs` 表落库 | 一次 Run 的全过程（每步工具调用、耗时、token）能查表复盘 |

**本阶段的学习要点（容易走偏的地方）**：

1. **M2 的验收标准不是"能跑"，是"模型决策正确"**。你要建一个 10~15 条的小评测集，其中**必须包含"不该调工具"的用例**（如"你好""谢谢"）。只测"该调的时候调对了"，会漏掉工具描述写得过于宽泛导致的误触发——这是 Agent 最常见的线上问题。
2. **先自研循环，不要一上来就用 Eino**。原因不是 Eino 不好，而是：你自己写过一遍循环之后，看 Eino 的文档是"哦它帮我做了这个"，学习速度是反过来的两倍；反过来先学框架，你只会照抄示例，遇到问题完全无法定位。
3. 工具描述（description）**写得越具体，误触发越少**。写"获取当前时间"比写"获取时间信息"好；加上边界说明"仅当用户明确询问当前时间时调用"效果更明显。

> ⚠️ **W10—W11 大概率撞上期末考**（各校校历不同）。这两周按 5h/周 的低强度执行，只做「配置类、验证类」任务（申请权限、跑通连通性），**不要在考试周写新模块**。如果确实撞了，把 M5 顺延到寒假第一周，寒假时间足够吸收。

**本阶段最容易卡住的三件事**（提前说，省得你怀疑人生）：

1. **飞书权限加了却不生效**——开放平台加权限点后必须**发布版本 + 管理员审批**。现象是 SDK 报 99991672（无权限）。这不是你的代码问题。
2. **Webhook 验签永远对不上**——九成是因为你用反序列化后再序列化的 body 去算签名。**必须保存原始字节**。
3. **长连接模式保存配置失败**——必须先启动本地客户端、保证有一条连接在线，再去后台点保存。顺序反了会卡住。

### 加分项 A：Eino 双引擎对比实验（强烈建议做）

按 7.0 节的设计，此时你的自研引擎已经跑了一个多月，工具业务逻辑都是现成的。引入 Eino 只需：

1. 定义 `Runner` 接口（自研版和 Eino 版各一个实现）；
2. 每个工具包一层 `tool.InvokableTool` 适配（业务代码一行不改）；
3. 用 `AGENT_ENGINE=selfbuilt|eino` 配置切换；
4. **跑同一批 30 条真实指令做对照**：工具调用准确率、平均步数、端到端延迟、token 消耗、失败恢复行为。

这直接构成论文的实验章节，**而且是唯一一份有你自己数据的对比实验**——大多数毕设做不到这一点，你顺手就有了。成本约等于一个适配层（1~2 周），性价比极高。

> 时间不够时的**降级顺序**（从先砍到后砍）：Eino 对比实验 → 卡片交互按钮 → CI 失败提醒 → 测试用例管理。**M1~M8 一个都不能砍**，那是论文的骨架。

## 9. 周节奏与周报机制

任务书明确要求「定期向指导教师汇报（每周至少 1 次）」。建议固定一个节奏，同时它也帮你自我检查：

| 时间 | 动作 |
|------|------|
| 周一晚 | 定本周 3 个目标（必须是可验证的，如"M7 去重表建好并通过单测"，而不是"推进提醒功能"） |
| 周二~周五晚 | 各 2 小时开发，当天 commit |
| 周六 | 整合、跑测试、补文档（**文档必须和代码同一周写，否则两周后你自己都看不懂**） |
| 周日 | 写周报（5 行：本周完成 / 遇到问题 / 下周计划 / 需要导师决策的事 / 数据快照） |
